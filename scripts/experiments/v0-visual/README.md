# V0 视觉批量建档离线实验脚本(Issue #3)

本目录是 issue #3「照片与短视频批量建档实验 v0」的**离线实验脚本骨架**:零产品代码,不改动小程序/云函数,不写 `items`,一切输出止步于「候选草稿 + 人工复核」。选型依据见 `docs/experiments/issue3-v0-model-report.md`。

## 目录

```text
scripts/experiments/v0-visual/
├── README.md            # 本文件:实验步骤、指标口径、隐私红线
├── probe-model.mjs      # 视觉模型连通性探针:单张测试图 → 多物品候选 JSON(无 key 打印指引退出)
├── extract-frames.sh    # ffmpeg 关键帧抽取:固定间隔 + 场景切换,参数可调
└── prompts/
    ├── single-image.md  # 单张照片的多物品候选 prompt 模板(B 方案)
    └── multi-frame.md   # 多帧(视频抽帧)候选去重 prompt 模板(C 方案)
```

## 依赖

- Node.js ≥ 18(probe 用内置 `fetch`,零 npm 依赖,不碰仓库 `node_modules`)
- ffmpeg / ffprobe(仅 C 方案抽帧用;B 方案不需要)

## 隐私红线(先读,实验全程有效;摘自 issue #3 合同第 7 条与 2026-10-10 增补 D 节)

1. **授权前不上传**:真实家庭照片/视频在明确授权并确认外部视觉服务商数据处理条款之前,不得发给任何模型 API。探针只允许使用非真实家庭影像的测试图(自拍静物、公开样图、合成图)。
2. **不留真实家庭影像**:实验原始素材与抽帧产物只放本地;公开渠道(Git 仓库、Issue 评论、日志输出)一律不出现真实影像与其可识别描述。写入 Issue 的统计只允许计数与脱敏样例。
3. **临时文件最短必要保留**:抽帧与压缩产物用完即清——

   ```bash
   ./extract-frames.sh --clean <输出目录>   # 或手动:rm -rf <输出目录>
   ```

   原视频/中间帧与用户主动保留的物品证据照片生命周期必须分开;实验结束统一删除。
4. 探针脚本绝不打印 API key,不把图片数据写进日志;只用环境变量传密钥。
5. 真实试用前必须补齐:外部视觉服务商的数据训练用途/保留期条款审查(报告「遗留与待验证」第 4 条)。

## 指标口径(照抄 issue #3「指标与 Exit」节,不得自行改定义)

- **单位正确建档时间 = 从启动拍摄/录入到最终确认完成总耗时 ÷ 最终核验正确入库件数**;A/B/C 三方案对比,报告每组样本数及区间。不能只比模型运行时间,也不能只数「识别出来几件」。
- 其他记录项:每区可见物品数、正确候选数、漏检、错误名称、重复/错误合并(**单列**)、错误位置归属(**单列**)、人工删改数、模型调用耗时/费用、上传及整批确认耗时。
- 主要晋升参考(GO 门):比逐件语音(A)降低约 30% 以上单位时间,且错误位置归属无不可接受劣化——预注册探索门,不是已知性能。
- 候选去重红线:**同名不盲并**——画面中两个相同充电器是两件物品;错误合并与重复创建都必须单列失败。不得把不可见/严重遮挡物品推测成「已存在」。

## A/B/C 三方案对照步骤

对每个实验区域(共 3 个真实抽屉/收纳箱)重复以下流程,记录到同一张统计表:

### 前置(一次性)

1. 人工清点每个区域的可见物品,**冻结参考金标清单**(标注不可见/严重遮挡物品),存本地,不推到公开仓库。
2. 准备 API key(见下「开跑前需要提供」),运行探针验证模型真实可用:

   ```bash
   node probe-model.mjs ./test-image.jpg            # 默认智谱 GLM-4.6V-Flash
   PROVIDER=dashscope node probe-model.mjs ./test-image.jpg   # 阿里对照
   ```

### A 基线:逐件语音(#1 已有链路)

用 PR #2 的逐件语音录入,对金标清单每件物品完整走「说话→等待→纠错→确认」。计时:从进入录入到全部确认完成。此方案不经过本目录脚本。

### B 方案:单张照片

1. 对区域拍一张照片(可多拍增补,每张单独跑)。
2. `node probe-model.mjs ./photo.jpg --prompt prompts/single-image.md`,记录候选 JSON、耗时、token 用量。
3. 人工对照金标清单逐条复核候选:改错名、删误检、补漏检、确认同名多件。计时:从启动拍摄到全部复核确认完成。
4. **不写 items**——结果只进统计表。

### C 方案:短视频 + 关键帧

1. 对同一区域拍 10–15 秒单一位置慢扫视频。
2. 抽帧(固定间隔 2s + 场景切换,预算 3–8 帧,可调):

   ```bash
   ./extract-frames.sh ./video.mp4 ./frames --interval 2 --scene 0.3 --max 8
   ```

3. 人工剔除模糊帧与明显重复帧(issue 合同:排除模糊、明显重复片段——这步计入 C 方案耗时)。
4. 将保留的帧按 `prompts/multi-frame.md` 发给模型(多图同请求;各模型多图上限见调研报告对照表),得到跨帧去重后的候选。
5. 同 B 的第 3–4 步复核与计时。
6. 用完即清:`./extract-frames.sh --clean ./frames`。

### 汇总

每区域每方案填一行:可见物品数 / 正确候选数 / 漏检 / 错误名称 / 重复 / 错误合并 / 错误位置归属 / 人工删改数 / 模型耗时与费用 / 总耗时 / 正确入库件数 → **单位正确建档时间**。脱敏后贴 Issue #3。

## probe-model.mjs 说明

- 密钥只从环境变量读,绝不硬编码:`BIGMODEL_API_KEY`(智谱)或 `DASHSCOPE_API_KEY`(阿里)。
- 没设 key 时:打印配置指引,以退出码 0 结束(与仓库 `tests/samples-live.js` 的先例一致),不会误报失败。
- 默认 `PROVIDER=zhipu`、`MODEL=glm-4.6v-flash`(免费,选型报告主选);`PROVIDER=dashscope` 时默认 `qwen3.8-flash`。可用 `MODEL=`、`API_URL=`、`API_KEY_ENV=` 覆盖任意 OpenAI 兼容端点。
- 输出:HTTP 状态、模型回复原文、用量(token 数,服务商返回时)、耗时。图片格式限 jpg/jpeg/png(智谱限制),超 5MB 会拒绝并提示。

## extract-frames.sh 说明

- 参数均可调:`--interval N`(固定间隔秒数,默认 2)、`--scene T`(场景切换阈值 0–1,默认 0.3)、`--max N`(总帧预算,默认 8,issue 示例预算 3–8)、`--quality Q`(JPEG 质量,默认 2)。
- 两路抽取:① `fps=1/interval` 固定间隔(若按默认间隔会超预算,自动放大间隔保证 ≤max);② `select='gt(scene,T)'` 场景切换帧。
- 产物:`interval_NNN.jpg` 与 `scene_NNN.jpg` 写入指定输出目录;`--clean` 删除整个输出目录。
- 脚本不自动删帧——模糊/重复帧的人工剔除是实验流程的一部分。
