## 证据 1:客户端直连 items 集合 —— 修复前(发现真实漏洞)

评审要求的探测落地后,确认权限设置过宽,**问题真实存在**:

| 探测 | 结果 | 含义 |
| --- | --- | --- |
| `wx.cloud.database().collection("items").get()` | `read-ok, count=6` | **任意客户端可直读全集合**,6 条为历史保留文档(软删测试数据与一条 bug 期空文档),含各家庭 name/location——跨家庭读取通道 |
| `wx.cloud.database().collection("items").add({data:{...}})` | `add-deny`,但拒绝原因是**唯一索引 E11000**(与既有空文档撞 null 键),非权限规则 | 权限层面写入同样开放;当前仅因一条 bug 期空文档占用 (null,null) 键而碰巧被挡,清掉该文档后写入即通 |

**修复动作**(控制台,无 CLI 通道):云开发控制台 → 数据库 → `items` → 权限设置 → 改为「**所有用户不可读不可写**」。所有业务访问都经云函数(管理端身份,不受权限规则约束),客户端不需要任何直连权限。

## 证据 3:两套真实微信身份交叉 —— 原记录作废与修正(2026-10-10)

**原「证据 3」作废**:昨日以真机记录「B侧测试物品」后从模拟器侧 query/list 为空,当时判定为交叉不可见。今日复核发现**该记录从未写入数据库**(用户在控制台找不到此文档)——对不存在记录的空结果不构成隔离证据(空洞为真)。

**今日实测揭示的事实**:用户提供真机新记录「B测试二号」的 _id 后,模拟器身份对其 get/update/delete **全部成功**。由于服务端所有读写都带 household_id 等值条件,这只能说明该文档与模拟器同属一个家庭空间:**开发者本人的手机微信(真机预览)与模拟器共享同一 openid**。即开发者一人无法构成第二身份,同身份读写成功是正确行为而非越权。

隔离**逻辑**本身仍由离线双身份测试覆盖(`tests/itemsApi.test.js`「越权」用例:注入两个不同 householdId,A 查 B 空、A 改/删 B 均 NOT_FOUND、B 数据无损),但真实环境的第二身份证据需要**另一个微信用户**参与(体验版 + 体验成员),见证据 4。
